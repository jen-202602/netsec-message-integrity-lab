# 消息协议与第一阶段设计

## 角色和传递过程

- Alice、Bob 使用同一个 `Endpoint` 实现，负责创建消息、维护各自发送序号、接收消息及保存收件箱。
- Evil 控制消息转发，当前实现原样返回收到的消息。后续在此处加入篡改与历史消息重放。
- `Simulation` 创建一个会话，并按发送、截获、转发、接收的顺序调用各角色，返回可供 CLI 和后续 GUI 显示的事件。

通信支持 Alice → Evil → Bob 和 Bob → Evil → Alice。每条消息都经过 `Evil.forward()`。收件箱保存实际转发到接收方的消息。

## 消息字段

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `version` | 整数 | 当前固定为 1 |
| `session_id` | 字符串 | 模拟器通过 `secrets.token_hex(16)` 生成，同一会话内保持一致 |
| `sender` | 字符串 | Alice 或 Bob |
| `recipient` | 字符串 | 另一通信端点 |
| `sequence` | 整数 | 从 1 开始，发送方每成功创建一条消息递增一次 |
| `content` | 字符串 | 消息正文，允许中文、空字符串和换行 |

Alice 和 Bob 分别维护发送序号。例如 Alice 发送两条、Bob 发送一条时，Alice 的消息序号是 1、2，Bob 的消息序号是 1。新建 `Simulation` 会创建新会话并重置双方序号。

消息对象不可变。后续篡改操作将构造修改后的消息，使原始发送内容与转发内容能够分别用于展示。

## 编码规则

`Message.to_bytes()` 将所有消息字段编码成 UTF-8 JSON。键名按字典序排列，使用紧凑分隔符，保留 Unicode 字符，不添加换行。正文保留调用方提供的字符内容。固定字段值会得到固定字节串，后续 HMAC 将使用该编码作为输入。

示例消息编码如下。

```json
{"content":"你好，Bob！","recipient":"Bob","sender":"Alice","sequence":1,"session_id":"demo","version":1}
```

## 当前处理规则

发送方创建消息时检查字段类型、角色名称和正整数序号。接收方检查消息的接收方名称，然后存入收件箱。相同消息重复投递时仍会被接收。

当前阶段的会话标识和序号用于标识消息。认证与接收端防重放检查将在后续阶段接入。

## 后续攻防设计

实验采用 Alice 与 Bob 预先通过可信方式共享密钥的假设。Evil 可以读取、修改和重放经过链路的消息。

计划自行实现 SHA-256 和 HMAC-SHA-256。认证标签将置于消息封装中，参与认证的内容包含上述全部消息字段。接收方验证认证标签后，再检查当前会话和发送序号，验证通过才更新防重放状态和收件箱。

GUI 将复用模拟器事件展示通信过程，单步执行阶段会将流程拆分为可推进的步骤。
