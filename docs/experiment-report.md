# 《计算机网络安全技术》课程实验一

# 中间人攻击与防御实验说明

项目名称为 `netsec-message-integrity-lab`，采用 Python 单进程模拟 Alice、Bob 和 Evil，提供命令行与 Tkinter 图形界面。实验场景为文本消息交换，围绕正文篡改、消息认证、历史消息重放及其防御展开。

## 一、运行环境与操作步骤

### 1. 运行环境

| 项目 | 配置 |
| --- | --- |
| 开发与验证系统 | Windows |
| 验证解释器 | Anaconda Python 3.10.9，64 位 |
| 项目要求 | Python 3.10 或更高版本 |
| GUI 组件 | 标准库 Tkinter，验证环境为 Tcl/Tk 8.6 |
| 程序依赖 | Python 标准库 |

| 对照运行环境报告 | OpenSSL 1.1.1t，7 Feb 2023 |

解压总提交包后得到 `program.zip` 与本实验说明。解压 `program.zip`，进入 `netsec-message-integrity-lab` 目录，再执行后续命令。所有相对路径均以该目录为起点。Windows 上也可用 `py -3` 替代 `python`。

GUI 需要可用桌面环境和 Tkinter/Tcl/Tk 组件，可先运行 `python -m tkinter` 检查组件是否正常。

### 2. GUI 操作

```powershell
python main.py --gui
```

1. 选择 Alice 或 Bob 作为发送方，填写正文。
2. 选择攻击方式“正常转发”“篡改正文”或“重放消息”，以及“无防御”“HMAC 认证”或“HMAC + 防重放”。篡改模式可填写 Evil 替换正文。
3. 点击“准备发送”，再用“单步执行”逐步推进。右侧角色高亮说明当前执行者，消息面板展示原始与当前正文和认证标签，事件列表记录完整过程。
4. 点击“自动播放”每 700 ms 推进一步。点击“暂停”后可以单步继续，也可再次自动播放。
5. 重放场景先完成一次正常投递，再由 Evil 原样重放缓存消息。空闲且存在缓存时，也可点击“重放最新缓存”，再推进实验。
6. 切换发送方可在同一会话内反向通信。切换攻击或防御方式会新建会话。“重置会话”取消执行与定时器，清空双方收件箱、缓存和事件记录。

设置区高度不足时使用右侧滚动条查看下方按钮。正文和消息对照区可滚动查看长文本。窗口展示双方收件箱数量和 Evil 缓存数量，便于核对被拒绝的消息是否影响状态。

可通过启动参数预选场景，也可通过模块启动 GUI。

```powershell
python main.py --gui --attack replay --defense hmac-replay --message "转账 100 元"
python -m lab.gui
```

## 二、功能实现与运行结果

### 1. 角色与通信模型

| 角色或模块 | 职责 |
| --- | --- |
| Alice、Bob | 创建消息、维护各自发送序号、生成与验证标签、检查接收新鲜性、保存收件箱 |
| Evil | 截获并转发消息、替换正文、缓存实际转发对象、再次注入历史消息 |
| `Simulation` | 创建会话、配置攻防模式、组织发送与接收步骤、产生可观察事件 |
| CLI 与 GUI | 使用同一模拟器，分别完整执行或逐步推进实验 |

消息通过 Alice → Evil → Bob 或 Bob → Evil → Alice 传递。所有攻击均在该转发路径中改变实际投递内容或再次注入缓存对象。收件箱仅在接收步骤成功时更新。

消息为不可变对象，包含协议版本、会话标识、发送方、接收方、序号、正文和认证标签。除标签本身外的六个字段使用键名排序、紧凑分隔符、保留 Unicode 的 UTF-8 JSON 编码，并一起参与 HMAC。标签独立于认证输入，避免自引用。

Alice 和 Bob 分别从序号 1 开始发送。模拟器使用 `secrets.token_hex(16)` 创建会话标识。启用 HMAC 时，通过 `secrets.token_bytes(32)` 创建随机共享密钥并交给双方，表示通信前已完成可信密钥分发。Evil 可观察明文与标签，转发接口仅接收消息对象。

### 2. 正常通信与篡改攻防

篡改模式下，Evil 在 `forward()` 中构造修改后的消息，将“转账 100 元”替换为“转账 900 元”，同时保留原标签。原始发送对象仍可用于消息对照。

| 场景 | 实际接收结果 | 收件箱变化 |
| --- | --- | --- |
| 正常消息，无认证 | 接收原始正文 | 增加一条 |
| 篡改消息，无认证 | 接收被替换的正文 | 增加一条 |
| 正常消息，HMAC | 认证通过，接收原始正文 | 增加一条 |
| 篡改消息，HMAC | 标签与修改后的字段不匹配，拒绝 | 保持原值 |
| 篡改消息，HMAC + 防重放 | 首先因认证失败拒绝 | 保持原值 |

消息被篡改时，原认证标签保持原值。接收方使用自己的共享密钥对实际收到的消息字段重新计算标签，并调用项目自行实现的验证函数比较。正常消息在两种认证模式下均可接收。

主要日志表现如下，会话和标签的具体随机值见程序包中的 `docs/validation.txt`。

```text
[Alice] 发送 | Alice -> Bob | 序号 1 | 正文 "转账 100 元"
[Evil] 篡改正文 | Alice -> Bob | 序号 1 | 正文 "转账 900 元"
无认证结果：Bob 已接收
启用 HMAC 后：Bob HMAC 认证失败，拒绝接收
```

相同正文替换后，编码字节保持一致，认证仍通过。验证中使用不同的原正文与替换正文展示篡改效果。

### 3. 重放攻击与防御（Bonus）

Evil 在首次转发时缓存消息对象，`replay()` 按历史索引重新取得该对象，并通过正常消息共用的接收流程再次投递。重放保留原正文、会话、序号及标签，历史缓存长度保持原值。

| 防御模式 | 第一次投递 | 第二次重放 | Bob 最终收件箱 |
| --- | --- | --- | --- |
| 无认证 | 接收 | 接收 | 2 条 |
| HMAC | 认证通过并接收 | 认证通过并接收 | 2 条 |
| HMAC + 防重放 | 认证通过并接收 | 认证通过，序号重复，拒绝 | 1 条 |

完整防御按以下顺序处理。

1. 验证认证标签。
2. 将消息会话标识与接收端配置的当前会话标识比较。
3. 要求消息序号严格大于该对端已接收的最大序号。
4. 全部通过后，更新接收序号并将消息写入收件箱。

序号允许跳号，例如 1、3 可依次接收，之后到达的 2 被拒绝。两个方向独立维护接收状态。认证失败、会话错误和重复序号均在状态更新前退出。测试用有效标签的旧会话消息单独验证会话检查，同时用伪造高序号验证攻击消息无法抬高接收状态。拒绝攻击后，后续合法双向通信仍然通过。

完整防御的重放阶段可观察到以下结果。

```text
[Evil] 重放已缓存消息，保留会话、序号和标签
[Bob] HMAC 认证通过
[Bob] 重复或过期序号，拒绝接收
重放结果：Bob 已拒绝 | 收件箱消息数 1
```

### 4. 单步执行与通信可视化（Bonus）

`send_steps()`、`replay_steps()` 和端点的 `receive_steps()` 使用惰性迭代器，每次推进时执行对应操作。原同步接口完整消费相同迭代器，CLI 和 GUI 共用实际攻防逻辑。

```text
发送 → Evil 截获 → 篡改（内容变化时）→ 转发 → 认证 → 接收或拒绝
```

准备发送阶段只创建迭代器。发送后，接收方收件箱保持原值；Evil 转发时才改变历史缓存；认证通过后可暂停；推进到接收时才改变接收序号和收件箱。GUI 使用 Tk `after()` 定时推进，暂停取消定时器，重置会话时取消当前流程并清空状态。

界面以角色高亮、消息对照、数量变化和带颜色的事件记录展示过程。实际桌面操作已验证自动播放下重放被拒绝、Bob 收件箱保持一条，以及滚动设置区后可访问重置按钮并清空记录。

### 5. 自行实现的密码算法

SHA-256 在 `lab/crypto/sha256.py` 中实现。处理过程包括追加 `0x80` 与零填充、追加原始位长度的 64 位大端表示、划分 64 字节分组、扩展 64 个消息字、执行 64 轮压缩、累加摘要状态并输出 32 字节结果。移位和加法使用掩码保持 32 位语义。实现依据为 FIPS 180-4。[FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)

HMAC-SHA-256 在 `lab/crypto/hmac_sha256.py` 中实现，内部调用项目的 SHA-256。超过 64 字节的密钥先取摘要，再补零至 64 字节，分别与 `0x36` 和 `0x5c` 组成内外层填充，计算下面的结果。[RFC 2104 第 2 节](https://www.rfc-editor.org/rfc/rfc2104#section-2)

```text
inner = SHA256((padded_key XOR ipad) || message_bytes)
tag   = SHA256((padded_key XOR opad) || inner)
```

两个算法接口均接收 `bytes`，输出 32 字节结果。文本调用方显式选择 UTF-8。验证函数检查完整标签长度，并对等长标签的全部字节累积异或差异后判断是否相同。

### 2. 主要问题及处理

SHA-256 的填充会在 56 字节附近改变分组数量，因此加入 55、56、57 字节及后续分组边界用例，逐字节比较标准库摘要。HMAC 长密钥先摘要再补零，通过 RFC 的 131 字节密钥用例和 64/65 字节边界交叉验证。

认证标签需要独立于待认证字段保存，消息编码固定排除 `auth_tag`。测试确认标签加入后认证输入保持一致，字段被修改时原标签失效。

仅 HMAC 模式的历史合法消息再次投递仍能通过认证。通过会话标识和接收最大序号补充新鲜性检查，并将全部状态更新放在验证之后，以避免错误消息影响后续接收。高序号伪造、有效认证的旧会话和后续正常消息构成相应回归用例。

为实现真实单步推进，将同步通信拆成惰性迭代器，并让 CLI 完整消费同一逻辑。测试在发送、截获和认证步骤检查收件箱，确认状态仅在接收步骤改变。

GUI 使用可取消的 `after()` 定时器实现播放和暂停。重置会话时取消回调并丢弃旧流程，通过事件循环测试确认结果。实际桌面检查发现小屏幕下设置区底部操作显示不足，随后加入自适应窗口高度与设置区滚动。隐藏测试窗口初始化后处理待执行布局事件，解决窗口销毁后的主题事件提示。
